# ULG 그래프 완료 승인 계획

작성일: 2026-10-03

## 1. 제품 동작 계약

ULG 그래프 기능은 아래 규칙을 만족해야 완료로 판정한다.

- 같은 분석 탭의 모든 **시간축 그래프**는 휠 줌, 박스 줌, 팬, 타임라인 범위 변경, 전체 줌 해제에서 함께 이동한다.
- 같은 ULG를 표시하는 여러 탭은 시간 범위와 시간 커서를 함께 이동한다.
- 서로 다른 ULG는 기본적으로 독립이다. 향후 비교 링크 기능을 켠 경우에만 로그 시작, Arm, Takeoff 또는 UTC 중 명시한 기준으로 정렬한다.
- 서로 다른 형식도 같은 창에 함께 적재할 수 있어야 한다. PX4 ULG가 열린 상태에서 ArduPilot DataFlash/TLOG 또는 ROS1/ROS2 로그를 추가해도 기존 그래프와 세션이 유지되어야 하며, 공통 숫자 신호는 한 패널에 겹쳐 비교할 수 있어야 한다.
- 교차 형식 비교의 기본 시간 기준은 각 로그의 `시작 후 경과시간`이다. UTC, Arm, Takeoff 정렬은 해당 기준 시각을 양쪽 로그에서 신뢰할 수 있을 때만 사용하며, 기준이 없으면 자동 추정하지 않고 사용자에게 `정렬 불가`를 표시한다.
- 2D/3D 공간 그래프의 카메라 줌은 시간 그래프의 X축 줌과 연결하지 않는다. 대신 시간 커서와 현재 위치 마커를 연결한다.
- 2D/3D 좌표 계약은 `X=East`, `Y=North`, `Z=Up`이다. PX4 local position의 NED `z`는 부호를 뒤집는다.
- 평가 결과는 그래프 표시와 별도 게이트로 검증한다. 신호가 없거나 전제가 성립하지 않으면 추측하지 않고 `평가 불가`로 표시한다.

## 3. 정량 합격선

### 시간 동기화와 반응성

- 연결된 그래프의 최종 X 범위 오차: `≤ 1e-6 s`, 화면상 `≤ 1 px`
- 휠 조작 중 follower 반영: `p95 ≤ 50 ms` 또는 2 frame 이내
- 마지막 입력 후 정확한 최종 범위 수렴: `≤ 100 ms`
- UI thread 입력 처리: `p95 ≤ 16.7 ms`, `p99 ≤ 33 ms`
- 단일 stall `>100 ms`: 0회
- 초기 3곡선 렌더: `≤ 500 ms`
- 패널 추가/분할: `≤ 200 ms`
- pan/reset commit: `≤ 100 ms`
- 기준본 대비 p95 회귀: `≤ 20%`

### 대용량 데이터

- 시간 그래프는 viewport 점 예산에 맞는 LOD를 선택하고 min/max peak를 보존한다.
- 2D 표시 점 수는 8,000 이하, 3D 표시 점 수는 5,000 이하를 기본 예산으로 한다.
- 다운샘플 후 첫 점, 마지막 점, 각 축 전역 최소·최대와 주요 방향 전환점을 보존한다.
- 100회 soak 뒤 RSS 증가는 `<100 MB` 또는 시작 대비 `<10%` 중 더 느슨한 기준 이하여야 한다.

### 2D/3D 정확도

- local 좌표 재배치 오차: `≤ 1e-6`
- global 위·경도 로컬 투영 오차: `≤ 0.5 m`
- 2D aspect ratio 오차: `<1%`
- 계산 경로 길이 상대 오차: `≤1%`
- 시간 마커 오차: 가장 가까운 sample 간격의 절반 이하

## 4. 평가 항목 타당성 체크

각 평가 항목마다 다음 근거를 결과물에 남긴다.

1. 입력 topic, field, 단위, 좌표계와 부호
2. 실제 평가에 사용한 비행 구간과 제외 구간
3. 계산식과 독립 reference 계산 결과
4. 정상/주의/문제 임계값의 출처와 바로 아래·같음·위 경계 시험
5. 그래프가 보여 주는 구간·데이터와 평가기가 사용한 구간·데이터의 일치
6. 결측, NaN, 센서 오류, 비행 모드 불일치 등의 confounder 처리
7. 표시 등급, 설명, 조언과 계산값의 일치

실제 두 ULG만으로 임계값 자체의 보편적 타당성을 확정하지 않는다. 두 파일은 계산·표시 일관성과 회귀 검증에 사용하고, 임계값 승인은 정상/고장 라벨이 있는 여러 기체·비행 조건의 별도 검증 세트로 수행한다.

## 5. 실행 조합

다음 두 비공개 검증 원본을 읽기 전용으로 사용한다. 공개 저장소에는 실제
파일명·경로·해시를 기록하지 않고 로컬 `runtime/test-artifacts/` 결과에만 남긴다.

- `private_validation_A.ulg`
- `private_validation_B.ulg`

각 파일 단독 및 두 파일 동시 조합을 cold/warm cache로 최소 3회 실행한다. 소스 실행과 packaged EXE를 모두 시험하며, 원본 SHA-256, 앱 Git revision, Python/Qt/OpenGL/GPU/DPI, 실행 시각을 결과에 기록한다.

## 6. 출시 순서

1. `ULG_STABLE`: 위 매트릭스의 자동 항목과 실제 Windows GPU 항목 통과
2. `MULTIFORMAT_PREVIEW`: ROS1, ROS2, ArduPilot DataFlash, TLOG, 표 로그를 형식별 opt-in으로 개방
3. `MULTIFORMAT_STABLE`: 각 형식의 실제 숫자 로그가 cold/warm cache와 같은 창 추가 적재·중첩·시간 정렬·제거 시험을 통과한 뒤 기본 사용자 진입점으로 승격
4. `PLATFORM_ANALYSIS_STABLE`: 형식별 semantic alias와 별도 평가 프로파일 검증 후 활성화

PX4 평가기는 이름이 비슷한 ROS/ArduPilot 신호에 자동 적용하지 않는다. ULG만 격리해 확인해야 할 때는 `ulg_stable` 정책을 명시한다.

## 7. 현재 기준 판정

2026-10-03 기준 판정은 다음과 같다.

- **ULG 자동 기능 승인 게이트: 통과.** 최종 전체 자동 회귀 결과는 `234 passed, 1 skipped`이다. skip 1건은 별도 MC 검증 로그 환경 변수가 없을 때 건너뛰도록 설계된 smoke 시험이다. 아래 `21/0`은 기능·범위·렌더 상태 판정이며 모든 성능 예산을 자동으로 강제하는 숫자는 아니다.
- **최종 ULG 출시 승인: 보류.** 100회 native GUI soak는 통과했으나, 아래의 실제 사용자 조작과 패키지 화면 시험이 남아 있다.
- **다중 형식 같은 창 비교: 기본 정책으로 승격.** `multiformat_stable`이 기본값이며 ULG, ROS1/ROS2, ArduPilot, CSV/JSON을 첫 화면에서 함께 노출한다. 형식별 의미론과 실제 사용자 조작 시험의 알려진 제한은 계속 추적한다.
- **평가 항목 의미론 승인: 부분 통과.** 확인된 오판정 네 종류는 수정했지만, 남은 항목 때문에 평가 점수를 기체 상태의 최종 판정서로 사용해서는 안 된다.

### 7.1 ULG 자동·실화면 실행 결과

비공개 원본은 이 문서에서 `private_validation_A.ulg`, `private_validation_B.ulg`로만 지칭한다. 실제 경로·파일명·해시는 ignored 로컬 결과물에만 기록한다.

- offscreen 자동 승인 실행: **21 passed, 0 failed**
- native Windows 화면 실행: **21 passed, 0 failed**
- native 2D 캡처에서 실제 경로색 픽셀을 각각 `12,216`, `1,312`개 확인해 빈 viewport가 아님을 검증
- 두 원본 모두 cold/warm cache 3회에서 숫자 신호 계약이 정확히 일치
- 한 패널의 1/2/3곡선 렌더: 최대 `124.047 ms`
- 1/2/3 시간 패널 생성과 범위 반영: 최대 `298.446 ms`, 최종 X 범위 오차 `0 s`
- 2D 경로: `68.603~71.793 ms`, 각각 `6,185`점과 `6,107`점
- offscreen projected 3D: `487.860~530.872 ms`, 원본당 `5,000`점
- native true OpenGL 3D 렌더: `173.267~225.468 ms`, 원본당 `5,000`점
- 서로 다른 두 ULG의 한 패널 중첩도 자동 실행에서 통과

native 실행의 `21/0`은 true-3D context 생성, 데이터 적재와 화면 렌더가 정상임을 뜻한다. 사용자가 마우스로 수행하는 3D 회전·팬·줌과 장시간 context 안정성까지 자동 승인했다는 뜻은 아니다.

native 실행에서 데이터 렌더와 범위 반영을 함께 잰 2/3패널 초기 구성은 최대 약 `476 ms`였다. 이는 순수 split 동작만의 시간이 아니므로 `200 ms` 예산과 일대일 비교할 수는 없지만, 패널 수가 늘 때 초기 화면 구성이 느려지는 병목 후보로 유지한다. 반복 휠 입력 경로는 아래처럼 별도로 계측했다.

### 7.2 연결 줌과 대용량 반응성

세 시간 패널에 30-notch 휠 입력을 연속 적용했을 때 결과는 다음과 같다.

| 입력 | callback p95 | follower 반영 p95 | 즉시/최종 범위 오차 |
|---|---:|---:|---:|
| `private_validation_A.ulg` | `2.380 ms` | `1.642 ms` | `0 s / 0 s` |
| `private_validation_B.ulg` | `3.903 ms` | `2.851 ms` | `0 s / 0 s` |
| 합성 250,001점 × 3패널 × 100회 | `7.769 ms` | `4.121 ms` | 최종 범위 정확히 일치 |

휠 callback 안에서 연결된 시간 그래프의 X 범위를 즉시 갱신하고, paint는 Qt event loop가 병합하도록 변경했다. 따라서 기존의 약 `300 ms` follower 정지는 재현되지 않았고 자동 기준을 만족했다. 다만 offscreen event-queue drain `81.189~96.682 ms`는 실제 frame time과 같은 값이 아니므로, 물리 휠 입력의 p95/p99와 체감 버벅임은 아래 수동 시험으로 확정한다.

### 7.3 100회 native GUI soak

`private_validation_A.ulg`을 Windows native Qt 환경에서 열고, 각 주기마다 `zoom → wheel idle commit → pan → reset → split → close`를 수행하는 100회 soak를 실행했다.

- **100/100회 통과:** crash, 미처리 예외, Qt critical, 주기 실패는 모두 0건
- 최종 연결 X 범위 오차 `0 s`, 전체 주기 최대 오차 `1.13686837721616e-13 s`, 종료 후 그래프 3개 유지
- 10회 간격과 첫·끝 주기의 native viewport를 캡처해 검은 화면·균일 화면 0건 확인
- RSS는 `616,341,504 B` → peak `702,230,528 B` → settled end `686,911,488 B`로, 최종 증가량은 `70,569,984 B` (`11.45%`)이다. 더 느슨한 기준인 `100 MiB` 이하를 만족해 RSS 게이트를 통과했다.
- callback p95는 zoom `14.424 ms`, pan `14.684 ms`, reset `18.184 ms`, split `306.651 ms`, close `10.162 ms`이다. split은 `200 ms` 목표를 넘어 최적화 후보로 남긴다.
- event-queue/paint drain p95는 zoom `329.058 ms`, pan `309.583 ms`, reset `320.898 ms`, split `691.802 ms`, close `508.769 ms`이다. 이 값은 해당 구간에 누적된 Qt event queue 전체를 비우는 진단값이며, 단일 frame latency나 사용자 체감 지연으로 해석하지 않는다.

초기 러너에서 발생한 pan 범위 오차는 실제 휠 수명주기의 idle commit을 생략한 테스트 경쟁 조건이었다. 실제 앱과 동일하게 `_handle_wheel_idle_transition()`을 적용한 뒤 40회 재현 시험과 최종 100회 시험이 모두 통과했다. 중간의 검은 캡처는 내용 확인 없이 non-null QScreen 결과를 채택한 러너 문제였으며, 이후 캡처 품질 판정과 desktop/OpenGL framebuffer fallback을 적용해 제거했다.

### 7.4 같은 창 다중 형식

프리뷰 단계에서 ULG, ArduPilot 계열 MAVLink TLOG, ROS1 bag, ROS2 bag을 한 세션에 동시에 적재한 실제 숫자 로그 시험을 통과했으며, 현재 `multiformat_stable`이 기본 정책이다.

- 한 패널에 네 원본의 곡선 네 개를 동시에 표시
- 범례를 `[형식 · 원본] topic.signal`로 구분하고 중복 없는 기본 색을 할당
- 서로 다른 샘플률과 길이를 유지하고, 전역 시간 범위를 모든 곡선의 합집합으로 계산
- 요청한 줌 범위와 관측 범위가 정확히 일치
- 한 원본 제거 시 나머지 곡선을 유지하고 전역 범위를 다시 계산
- 제거한 원본 재적재 시 곡선과 범위를 복원
- PX4 전용 평가기는 ROS/ArduPilot 신호에 실행되지 않고 `평가 불가`로 격리
- 손상된 TLOG·ROS1·ROS2 적재 실패가 기존 PX4 데이터·곡선·범위·트리를 변경하지 않음
- 여러 파일을 한 번에 열 때 일부만 성공해도 실패 파일과 원인을 알리고 성공 파일만 반영
- UI 트리 반영 중 예외가 발생하면 데이터·형식·메타데이터·활성 로그·트리 상태를 모두 롤백

이 결과는 **같은 창의 적재·중첩·줌·제거 계약**에 대한 preview 승인이다. 신호의 의미나 단위가 다른 곡선을 자동으로 같은 물리량이라고 간주하지 않으며, 이벤트/UTC 정렬도 주장하지 않는다. 또한 실제 ArduPilot DataFlash 원본에 대한 별도 cold/warm·시각화 회귀가 끝나기 전에는 `MULTIFORMAT_VISUALIZATION_STABLE`로 승격하지 않는다.

### 7.5 평가 항목 수정 결과와 잔여 위험

독립 계산과 경계 시험을 통해 다음 네 오판정을 수정했다.

- 경로 추종은 actual-setpoint 위치 차이를 횡방향 오차로 오인하지 않고 `npfg_status.signed_track_error`를 우선 사용
- TAS 비교는 GPS 지상속도에서 바람을 제거하고 cruise 필터의 degree/radian 조건을 바로잡음
- transition 고도 손실은 전환 시작 고도보다 아래로 내려간 구간만 손실로 계산
- controller saturation은 armed·airborne 구간의 정규화된 `actuator_motors`만 사용하고 raw PWM percentile을 물리 한계로 간주하지 않음

대표적인 회귀 변화는 아래와 같다.

| 항목 | `private_validation_A.ulg` | `private_validation_B.ulg` |
|---|---:|---:|
| controller saturation | `41.843% → 0.075%` | `35.729% → 0.093%` |
| airspeed RMS | `2.435 m/s → 0.687 m/s` | `3.651 m/s → 0.476 m/s` |
| transition 고도 손실 | `1.922 m → 0.215 m` | `4.079 m → 0.00045 m` |
| NPFG 횡방향 오차 평균 | `6.146 m` | `6.195 m` |

현재 전체 점수 `84.0`, `86.1`은 회귀 비교용 출력이며 최종 안전성·성능 인증값이 아니다. 다음 항목은 추가 검증이 필요하다.

- telemetry lost-rate의 단위와 의미
- VTOL TECS/고도 평가의 phase gate
- battery, CPU, dropout 결측 시 판정
- attitude 축 평균 방식과 yaw wrap
- rotor/coupling 휴리스틱
- 데이터 신뢰도가 전체 점수에 반영되지 않는 문제

### 7.6 최종 수동 승인 대기 항목

다음 네 항목이 모두 통과해야 `ULG_STABLE` 완료로 판정한다.

1. 실제 마우스로 true OpenGL 3D 회전·팬·줌을 반복하고 context 안정성 확인
2. 실제 휠 입력의 p95/p99 paint latency와 주관적 버벅임 확인
3. packaged EXE를 Windows 100%/150% DPI에서 실행해 글자·범례·2D/3D 화면 확인
4. 동일 3D Path에서 Auto/Fixed Wing/Quadcopter/Helicopter/Rover를 연속 전환하고, 마커 형상·기수 방향·배율·레이아웃 복원을 확인
